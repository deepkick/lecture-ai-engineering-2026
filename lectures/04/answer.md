## 宿題

- 取り組んだレベル：発展（SWE-bench Verified）

- 目的：フロンティアモデルの評価に使われてきたベンチマークを1つ読み、今日の評価セット（10 件、講師 1 人が作成、人と LLM で採点）と作り方を比べる。確かめたい問いは次の2つ。
  1. 問題は何を問い、どこが難しいか。
  2. 誰が何人で、どう作り、どう検証・採点したか。今日の評価セットとどう違うか。

- やったこと：
  - データセット：[SWE-bench Verified（Hugging Face）](https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified)。難易度の違う5件を読んだ（うち3件は、OpenAI が 2026 年に不備や混入の例に挙げた問題）。
  - 元の論文（C. E. Jimenez et al., ICLR 2024, arXiv:2310.06770）と OpenAI の記事2本（2024/8「Introducing SWE-bench Verified」、2026/2「Why SWE-bench Verified no longer measures frontier coding capabilities」）で、作成・検証・採点の手順を調べた。

- 結果：
  - **問い1**：issue の文章とリポジトリだけを渡され、テストを見ずに直す課題。5件中3件は、合格するのに issue に書かれていない仕様（引数名・関数名・別の issue の機能）が必要で、難しさは実装より「仕様を当てること」にあった。

    | 問題 | 難易度 | 内容（要約） | 自分なら解けるか（issue を読んだ見立て） | LLM にとって難しい点 |
    |---|---|---|---|---|
    | pallets__flask-5014 | 15 分未満 | 空の Blueprint 名で ValueError を出す | 解ける。PR でも確認し、修正は既存の名前チェックの隣に 3 行足すだけで、テストも issue の仕様どおり | ほぼない |
    | django__django-14725 | 15 分〜1 時間 | フォームセットで新規作成を禁止する手段がほしい | 方針は分かるが、引数名 `edit_only` は当てられない | テストが issue に無い引数名を使う |
    | sympy__sympy-18199 | 1〜4 時間 | `nthroot_mod` が根 x = 0 を返さない | x = 0 は直せるが、テストには通らない | テストが問題文に無い機能を見る（広すぎるテスト） |
    | pylint-dev__pylint-4551 | 1〜4 時間 | pyreverse の図に型ヒントを出したい | 内部を読むのに時間がかかる | テストが issue に無い関数名を import する（狭すぎるテスト） |
    | sphinx-doc__sphinx-7590 | 4 時間超 | C++ のユーザー定義リテラルを解析できない | 難しい | 大きな構文解析器を読み、直す範囲を自分で決める必要がある |

  - **問い2**：
    - 作成：人気の Python リポジトリ 12 個の約 9 万件の PR から、テストの実行結果で自動的に 2,294 件に絞った（元の SWE-bench。人手はほぼ使わない）。
    - 検証：Python の経験がある開発者 93 人が、1,699 件を 1 件につき 3 人で独立に審査した。3 人のうち 1 人でも重い問題（記述が不十分、テストが正しい解答を落とす）を指摘したら除外し、68.3% を落として、残りから 500 件を選んだ。
    - 採点：テストの実行（コード）だけ。人も LLM も採点しない。
    - その後：2026 年の再監査で、o3 が解けなかった 138 件の 59.4% に不備が見つかり、学習データへの混入も確認されて、OpenAI は報告をやめた。

    | | 今日の評価セット | SWE-bench Verified |
    |---|---|---|
    | 規模 | 10 件 | 500 件（審査は 1,699 件） |
    | 作った人 | 講師 1 人 | 自動の抽出 ＋ 開発者 93 人の審査 |
    | 採点 | LLM（4 基準）＋ コード（1 基準） | テストの実行（コード）だけ |
    | 人が確かめること | LLM の判定が人と一致するか | テストが正しい解答を落とさないか |
    | 曖昧なケース | 残して unsure にし、基準を直す | 捨てる（68.3% を除外） |

- 気づき・疑問：
  - **人が検証する対象が違う。** Verified は採点器（テスト）が公正かを、演習は採点器（LLM）が人と合うかを確かめている。どちらも恐れているのは「正しいものを落とす」こと（演習でいう過検出）だった。
  - **曖昧なケースの扱いが逆なのは、目的の違いから来る。** モデルを比べる物差しは「誰がやっても同じ合否になる」問題だけを残す。自分のアプリを直すための評価では、本番で来る曖昧な質問を捨てられないので、unsure として残して基準を育てる。
  - **3 人で審査しても不備は残り、見つかったのはモデルが解けなかった問題を読んだときだった。** 自分の評価セットでも、不合格を読むときは、回答だけでなく基準や参照の側を疑う。
  - 疑問：Verified は曖昧な issue を捨てたので、「推測で進めずに確認する」能力は測っていない。この能力を測るベンチマークはあるのか。
